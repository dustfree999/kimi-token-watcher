# Kimi Code Token 监控组件完善建议

## 1. 文档说明

本文档基于当前项目中的以下组件进行整理：

- `app.js`：前端监控逻辑、图表、明细、实时事件流、定价设置
- `server.py`：本地数据采集、日志增量扫描、统计聚合、HTTP 服务
- `index.html`：页面结构与 Dashboard 信息架构
- `style.css`：深色数据面板与响应式样式
- `data.json`：本地持久化数据

当前组件已经具备较完整的监控能力，包括今日 / 7 天 / 30 天统计、Token 趋势、主 / 子智能体统计、模型与会话明细、历史数据、实时事件流以及本地定价配置。

当前阶段重点不是继续堆叠基础功能，而是优先提升**统计准确性、实时监控能力、长期运行稳定性以及移动端体验**。

# 3. P0：必须优先修复的问题

## 3.1 usage.record 去重指纹过粗

### 当前实现

当前 `usage.record` 的去重指纹主要由以下字段组成：

```text
(time, model, inputOther, output, cacheRead, cacheCreation)
```

如果两个不同会话或不同 Agent 在同一时间点产生完全相同的 Token 统计数据，就可能被错误识别为同一条记录。

### 风险

例如：

```text
16:20:01.123  session_A  deepseek  input=1000  output=500
16:20:01.123  session_B  deepseek  input=1000  output=500
```

第二条可能被去重逻辑直接丢弃，从而造成 Token 少算。

### 建议

优先使用日志自身提供的稳定唯一字段，例如：

```text
request_id
event_id
message_id
turn_id
```

如果原始日志没有这些字段，则至少使用以下组合构造唯一标识：

```text
session_id + agent + timestamp + model + sequence
```

不要只依赖时间戳和 Token 数值。

### 验收标准

- 不同 session 同时产生相同 Token 数据时，两条都能被统计。
- fork 场景仍然能够正确去重。
- 重启服务后不会重复统计历史数据。

---

## 3.2 llm.request 去重条件过于简单

当前 request 级别主要采用：

```text
(time, model)
```

作为去重依据。

这种方式比 usage.record 的问题更加明显，因为不同 session 使用相同模型并在同一毫秒发起请求时，很容易发生误去重。

### 建议

改为：

```text
session_id + request_id
```

或者在没有 request_id 时使用：

```text
session_id + timestamp + model + sequence
```

### 验收标准

并发主 Agent / 子 Agent 请求不会互相覆盖。

# 4. P1：数据统计与监控体验优化

## 4.1 实时事件展开状态不要使用 time 作为唯一 Key

当前前端使用：

```js
expandedEvents.has(ev.time)
```

保存事件的展开状态。

如果多个事件拥有相同时间戳，则可能出现展开状态串联的问题。

### 建议

为每条事件生成稳定 `eventId`：

```text
session_id + timestamp + sequence
```

前端统一使用：

```js
expandedEvents.has(eventId)
```

---

## 4.2 “当前速率”指标定义需要调整

当前后端的速率实际上是：

```text
当前小时累计 Token ÷ 当前小时已经过去的分钟数
```

它更接近：

> 本小时平均 Token 速率

而不是严格意义上的“当前实时速率”。

### 建议

增加滚动窗口速率：

```text
最近 1 分钟
最近 5 分钟
最近 15 分钟
```

推荐 UI：

```text
当前速率
128k / min
↑ 18.4%
```

这样可以更真实反映当前使用强度。

---

## 4.3 完善缓存写入成本统计

后端已经记录：

```text
inputOther
inputCacheRead
inputCacheCreation
output
```

但当前费用计算主要覆盖：

```text
输入未命中
缓存读取
输出
```

因此 `inputCacheCreation` 当前没有完整进入费用计算模型。

### 建议

费用模型统一拆成：

```text
输入未命中
缓存读取
缓存写入
输出
```

定价设置窗口增加：

```text
缓存写入：¥ / 百万 tokens
```

并同步更新：

- 总费用
- 历史费用
- 模型费用
- 会话费用
- 明细 Tooltip

# 5. P1：长期运行稳定性

## 5.1 data.json 数据增长治理

当前服务会持续保存：

- 每日统计
- 文件偏移量
- 去重指纹
- 历史聚合数据

去重集合虽然已经存在 30 天清理机制，但长期使用后仍然建议对持久化结构进行治理。

### 建议

增加数据保留策略，例如：

```text
7 天：原始级明细
30 天：完整聚合
90 天：日级聚合
90 天以前：归档或删除
```

前端历史区域默认只显示最近 30 天，并提供：

```text
7 天 / 30 天 / 90 天 / 全部
```

---

## 5.2 保存策略可以进一步增强

当前状态大约每 30 秒持久化一次。

建议增加以下策略：

### 正常运行

保持当前定时保存机制。

### 重要状态变化

发生以下情况时立即保存：

- 服务退出
- 文件被截断
- 数据结构变化
- 采集异常恢复

### 写入方式

继续保持临时文件 + 原子替换：

```text
数据 → data.json.tmp → os.replace()
```

这种方式可以减少半写入状态造成的数据损坏。

# 6. P1：实时事件流增强

当前实时事件流已经具备：

- 时间
- 主 / 子 Agent
- 模型
- Token
- Session
- 输入文本
- 输出文本
- 点击展开
- 新事件高亮

这部分基础体验已经很好。

## 建议增加

### 6.1 事件类型

例如：

```text
USAGE
REQUEST
TOOL
ERROR
```

方便排查异常。

### 6.2 一键复制

展开事件后提供：

```text
复制输入
复制输出
复制全部
```

### 6.3 事件过滤

增加：

```text
全部
主 Agent
子 Agent
指定模型
异常
```

### 6.4 暂停自动滚动

当用户向下查看历史事件时，不应强制每 2 秒回到顶部。

建议：

```text
自动滚动：开启 / 暂停
```

发现用户手动滚动后自动暂停，回到顶部后恢复。

# 7. P2：前端渲染性能

当前前端采用 2 秒轮询：

```text
fetch('/api/usage')
↓
render()
↓
重新构建整个 Dashboard
```

目前数据量较小时问题不明显，但长期运行后会增加 DOM 重建开销。

## 推荐升级路径

### 第一阶段

保持 2 秒轮询，但进行局部更新：

```text
指标 → 直接更新
图表 → 数据变化后更新
模型 → 数据变化后更新
事件 → 只追加新增事件
```

### 第二阶段

使用 Server-Sent Events：

```text
Python Server
     ↓
     SSE
     ↓
 Browser
```

对于本地监控工具，SSE 已足够满足实时数据推送需求。

不建议当前阶段为了“实时性”直接引入复杂 WebSocket 架构。

# 8. P2：移动端体验

当前已经有多个媒体查询，对响应式进行了基础适配。

但模型表、会话表、实时事件流仍然明显偏向桌面端。

例如实时事件当前信息密度较高：

```text
时间 | 类型 | 模型 | Token | Session
```

在手机宽度下容易出现拥挤。

## 推荐方案

桌面端保持表格结构。

移动端切换为卡片结构：

```text
16:32:04
主 · DeepSeek

输入       12.4k
缓存        8.3k
输出        2.1k

会话：xxxxx
```

这样信息可读性会明显提升。

---

# 9. P2：顶部指标建议增加“趋势”能力

当前顶部指标已经包含：

```text
今日总 Tokens
费用估算
缓存命中率
请求次数
峰值小时
当前速率
```

建议增加一个趋势类指标：

```text
较昨日
↑ 31.4%
```

或者：

```text
今日消耗
12.8M
↑ 31.4% vs 昨日
```

这样 Dashboard 会从单纯的：

> 数据展示

升级为：

> 数据监控 + 趋势判断

# 12. 最终验收标准

完善完成后，建议至少验证以下场景：

### 数据准确性

- [ ] 两个 Agent 同时产生相同 Token 数据不会少算
- [ ] 同一条日志重复扫描不会重复统计
- [ ] fork 会话不会重复累计父会话历史
- [ ] 服务重启后数据保持一致
- [ ] 文件截断 / 重建后不会严重重复统计

### 实时性

- [ ] 新事件约 2 秒内可见
- [ ] 事件详情展开状态在刷新后保持
- [ ] 用户手动浏览事件时不会被强制拉回顶部
- [ ] 连接异常有明显提示

### 费用

- [ ] 输入未命中费用正确
- [ ] 缓存读取费用正确
- [ ] 缓存写入费用正确
- [ ] 输出费用正确
- [ ] 修改定价后历史费用同步变化

### 性能

- [ ] 长时间运行不会明显卡顿
- [ ] 100+ session 时页面仍然可用
- [ ] 500 条事件流滚动正常
- [ ] data.json 长期增长可控

### UI

- [ ] 1920×1080 桌面正常
- [ ] 1440×900 正常
- [ ] 1024×768 正常
- [ ] 手机宽度不出现横向溢出

# 13. 结论

当前组件已经达到“可用且比较完整”的阶段，下一步不建议继续大幅增加新的 Dashboard 模块。

真正需要优先投入的是：

> **数据准确性 → 实时指标 → 费用模型 → 长期运行 → 移动端体验**

其中最关键的是去重机制。目前 `usage.record` 和 `llm.request` 的去重指纹仍然存在误判边界条件，这属于数据层问题，应优先解决。

完成上述 P0 / P1 项后，这套组件基本可以稳定作为一个长期运行的 **Kimi Code Token 本地监控 Dashboard** 使用。
